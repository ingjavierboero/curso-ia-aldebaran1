# PRD-001: Aldebaran — Un sistema para gestion de clientes y pagos

## Contexto y Problema
Mi empresa vende Software as a Service. Hoy el proceso de cobro lo estoy llevando yo a mano, generando las facturas de cobro todos los meses, enviando a los clientes los emails con las facturas y los resumenes de deuda y ademas despues controlo los pagos cuando el cliente me envia por mail el cupon de pago.
Necesito un sistema que me permita gestionar la facturacion y los cobros de manera automatizada, generando todos los meses las diferentes facturas contra ARCA, enviarselas a los clientes por mail y controlar que el pago se haya realizado.

## Objetivos
El 100% de las facturas deben ser enviadas a los clientes el dia 15 de cada mes
El 100% de los pagos recibidos deben ser controlados por el sistema
La intervencion del usuario debe ser minima solamente para confirmar el pago de la factura

## Requerimientos Funcionales
- RF-01: El sistema debe tener un ABM de usuarios con perfiles Admin, Consulta, Editor
- RF-02: El sistema debe tener un ABM de clientes
- RF-03: El sistema debe tener un ABM de sistemas
- RF-04: El sistema debe permitir asignar uno o varios sistemas a un cliente
- RF-05: El agente debe generar todos los dias 15 de cada mes la factura correspondiente en ARCA para todos los clientes con el detalle de las cuotas mensuales de todos los sistemas contratados
- RF-06: Una vez generada la factura, el agente debe enviarsela a los clientes a sus mails registrados informando que tiene una deuda pendiente
- RF-07: Una vez enviada la factura, el agente debe controlar diariamente la casilla de email verificando si se recibio respuesta por parte del cliente con el cupon de pago/transferencia
- RF-08: El sistema debe utilizar un LLM para leer el contenido del email y el documento adjunto en caso de tenerlo para saber si se realizo el pago correspondiente a la factura
- RF-09: En caso de que el LLM determine que el email recibido corresponde a un pago, el agente debe controlar que el CUIT y el monto del comprobante coincidan con los de la factura enviada
- RF-10: Si el CUIT y el monto coinciden, el agente debe marcar la deuda como "Pago recibido" para que un usuario la controle y la marque como saldada
- RF-11: el sistema debe permitir al usuario marcar las deudas con "Pago recibido" como "Pagada"
- RF-12: El agente debe recordar la deuda vigente a los clientes deudores con un 2do mail el ultimo dia de cada mes en caso de corresponder
- RF-13: El sistema debe tener un dashboard en donde se presenten aquellos clientes que presentan deuda vigente con la posibilidad de enviar un recordatorio por mail manualmente
- RF-14: El sistema no debe enviar ningun email a un cliente que no tiene sistema asignado.
- RF-15: El sistema no debe enviar ningun email si el cliente no presenta deuda vigente.
- RF-16: El sistema no debe enviar el email recordatorio automatico de fin de mes si el cliente ya saldo su deuda.
- RF-17: El sistema no debe permitir enviar el email recordatorio manual desde el dashboard si el cliente no presenta deuda en ese momento.
- RF-18: El sistema debe permitir que los precios de los sistemas se fijen en pesos o dolares
- RF-19: en caso de que el sistema fije precio en dolares, la factura debe hacerse en pesos tomando la cotizacion del dolar blue para la venta de la pagina dolarhoy.com

## Requerimientos No Funcionales
- RNF-01: El procesamiento del email de respuesta debe hacerse en menos de 1 minuto.
- RNF-02: En caso de falla del LLM se debe reintentar hasta 3 veces antes de marcar el proceso como erroneo
- RNF-03: El proceso de facturacion mensual debe completarse el mismo dia 15 antes de las 22 hs
- RNF-04: La API key del modelo no debe estar en el codigo; se lee de la variable
  de entorno ANTHROPIC_API_KEY.
- RNF-05: Las contraseñas deben almacenarse con hash seguro (bcrypt/argon2), nunca
  en texto plano; la sesion expira tras 24 h de inactividad.

## Criterios de Aceptacion

- AC-01 (RF-01): Dado un usuario con perfil Admin autenticado, cuando crea un nuevo usuario asignandole el perfil Editor o Consulta, entonces el usuario queda registrado, puede iniciar sesion y sus acciones disponibles quedan restringidas a las permitidas por ese perfil (Consulta: solo lectura; Editor: ABMs pero no gestion de usuarios; Admin: todo).
- AC-02 (RF-02): Dado un usuario con perfil Admin o Editor, cuando completa el alta de un cliente con sus datos obligatorios (razon social, CUIT, email de facturacion), entonces el cliente queda visible en el listado con estado "activo" y disponible para asignarle sistemas.
- AC-03 (RF-03): Dado un usuario con perfil Admin o Editor, cuando da de alta un sistema indicando nombre y precio de la cuota mensual, entonces el sistema queda disponible en el ABM para ser asignado a uno o mas clientes.
- AC-04 (RF-04): Dado un cliente activo y uno o mas sistemas dados de alta, cuando un usuario Editor le asigna dichos sistemas al cliente, entonces el cliente queda vinculado a esos sistemas y el monto de la proxima factura se calcula como la suma de las cuotas de los sistemas asignados.
- AC-05 (RF-05): Dado que llega el dia 15 de cada mes, cuando el agente ejecuta el proceso de facturacion, entonces se genera en ARCA una factura por cada cliente con al menos un sistema asignado, con el detalle de cada cuota mensual incluida, y la factura queda registrada en el sistema con estado "pendiente de pago".
- AC-06 (RF-06): Dado que se genero correctamente una factura para un cliente, cuando el agente finaliza ese proceso, entonces se envia un email a la casilla registrada del cliente informando el monto adeudado, y queda registrado el envio (fecha, hora y destinatario) en el historial del cliente.
- AC-07 (RF-07): Dado que se envio el email de factura a un cliente con deuda pendiente, cuando transcurren los dias de control configurados, entonces el agente revisa la casilla de correo del sistema y deja registro de la revision, detectando si hubo o no una respuesta del cliente con el cupon de pago.
- AC-08 (RF-08): Dado un email de respuesta del cliente, con o sin adjunto, cuando el agente lo procesa con el LLM, entonces determina si el contenido corresponde a un pago de la factura enviada; si no hay certeza suficiente, no lo marca como pago sino que lo deja pendiente de revision manual.
- AC-09 (RF-09): Dado que el LLM determino que el email corresponde a un pago, cuando el agente compara el CUIT y el monto informados contra los de la factura enviada, entonces solo continua el proceso si ambos coinciden; si no coinciden, deja el caso para revision manual sin registrar el pago.
- AC-10 (RF-10): Dado que el CUIT y el monto coinciden con la factura, cuando el agente confirma la validacion, entonces la deuda queda marcada como "Pago recibido" a la espera de que un usuario la confirme.
- AC-11 (RF-11): Dado una deuda en estado "Pago recibido", cuando un usuario Admin o Editor la revisa y confirma, entonces la deuda pasa a estado "Pagada" y esa factura deja de generar recordatorios.
- AC-12 (RF-12): Dado un cliente con deuda vigente al ultimo dia del mes, cuando el agente ejecuta el proceso de recordatorios, entonces se envia un segundo email recordatorio solo a los clientes que a esa fecha no estan en estado "Pagada".
- AC-13 (RF-13): Dado un usuario autenticado en el dashboard, cuando visualiza el listado de clientes con deuda vigente y selecciona "enviar recordatorio" sobre uno de ellos, entonces se dispara el envio manual del email y queda registrada la accion junto con el usuario que la ejecuto.
- AC-14 (RF-14): Dado un cliente sin ningun sistema asignado, cuando se ejecuta el proceso mensual de facturacion y envio, entonces no se genera factura ni se envia ningun email para ese cliente.
- AC-15 (RF-15/RF-16): Dado un cliente sin deuda vigente (nunca facturado o ya en estado "Pagada"), cuando corresponde el envio del recordatorio automatico (mensual o de fin de mes), entonces el sistema no envia ningun email para ese cliente.
- AC-16 (RF-17): Dado un cliente sin deuda vigente, cuando un usuario intenta forzar el envio manual del recordatorio desde el dashboard, entonces el sistema bloquea la accion y muestra un mensaje indicando que el cliente no tiene deuda pendiente.
- AC-17 (RF-19): Dado un cliente con un sistema asignado cuyo precio esta fijado en dolares, cuando el agente genera la factura mensual, entonces convierte ese monto a pesos usando la cotizacion del dolar blue venta de dolarhoy.com vigente al momento de facturar, y esa cotizacion queda registrada en la factura para poder verificarla despues.

## Fuera de Alcance
- El agente no debe controlar los pagos accediendo a ningun sistema bancario ni realizando consultas de movimientos de cuenta. Solamente se marca como pagado cuando llega un email de respuesta por parte del cliente adjuntando el cupon de pago

## Riesgos y Dependencias
- Riesgo: La factura no se puede generar en ARCA → mitigacion: Se alerta al usuario con un banner en el dashboard principal.
- Riesgo: No se pueden enviar los emails → mitigacion: Se alerta al usuario con un banner en el dashboard principal.
- Riesgo: dolarhoy.com no responde o cambia su formato al momento de facturar (no es una API oficial) → mitigacion: usar la ultima cotizacion registrada y alertar al usuario con un banner en el dashboard principal para que la confirme.
- Dependencia: API de Claude · SQLite · dolarhoy.com (cotizacion del dolar blue).
